# 后端多应用架构优化方案 (基于参考结构)

## 一、方案概览 (Summary)

参考您提供的多应用架构 (app/ 顶层独立应用 + plugin/ 顶层插件 + 5 个横切复用目录),将当前后端从**单应用 + 3 层架构**重构为**多应用 + 横切关注点**架构。核心思路是:

- **`app/` 顶层** = 独立业务应用 (Bounded Context),每个应用自治
- **`plugin/` 顶层** = 独立可插拔扩展 (与 app 平级,可被各 app 加载)
- **5 个横切目录 (common/core/database/middleware/utils)** = 共享基础设施,所有 app 复用

这种架构的优势: **多应用隔离清晰、插件化能力强、关注点彻底分离、易于团队协作**。

## 二、参考架构核心特征解读

### 2.1 您提供的结构解析

```
backend/
├── app/                           # 业务应用集合 (顶层, 独立 Bounded Context)
│   ├── admin/                     # 应用 1: 管理系统
│   └── tasks/                     # 应用 2: 任务系统
├── plugin/                        # 插件 (与 app 平级)
├── common/                        # 公共组件 (复用)
├── core/                          # 核心配置 (复用)
├── database/                      # 数据库配置 (复用)
├── middleware/                    # 中间件 (复用)
└── utils/                         # 工具函数 (复用)
```

**关键解读**:

| 目录 | 层级 | 含义 |
|---|---|---|
| `app/` | 业务应用 | 每个子目录是一个独立应用, 自带完整技术栈 (api/service/model) |
| `plugin/` | 业务扩展 | 独立插件, 可挂载到任何 app |
| `common/` | 横切复用 | 业务相关的可复用组件 (如 BaseModel, 业务枚举) |
| `core/` | 横切复用 | 应用配置 (pydantic settings, 环境变量) |
| `database/` | 横切复用 | 数据库连接、会话、迁移、ORM 基类 |
| `middleware/` | 横切复用 | FastAPI 依赖、中间件、错误处理 |
| `utils/` | 横切复用 | 纯函数工具 |

### 2.2 与我上一版方案的关键差异

| 维度 | 上一版方案 | 您提供的新结构 |
|---|---|---|
| 应用层 | `apps/annotation/`, `apps/training/` 等 11 个 | `app/admin/`, `app/tasks/` (按职责大类分) |
| 插件位置 | `apps/{domain}/plugins/` 内嵌 | `plugin/` 顶层独立 |
| 横切目录 | `infrastructure/` + `shared/` 合并 | `common/ core/ database/ middleware/ utils/` 5 个独立顶层 |
| 数据访问 | `apps/{domain}/models.py` 内嵌 | `database/` 顶层 (orm 基类、连接) + 应用内 model |
| 业务编排 | 显式 `services/{domain}_service.py` 顶层 | 应用内部组织 (无独立 service 层) |
| ORM 模型归属 | 应用内 | 应用内 (但基类在 database/) |

### 3.2 顶层目录职责矩阵

| 目录 | 职责 | 依赖 | 不应包含 |
|---|---|---|---|
| `app/` | 独立业务应用 (Bounded Context) | common, core, database, middleware, utils, plugin | 跨应用业务逻辑 |
| `plugin/` | 可插拔扩展 (认证/存储/ML/队列) | common, core, database, utils | 业务逻辑 |
| `workers/` | 异步任务入口 (薄) | app/*, plugin/task_queues, database | 业务实现 |
| `common/` | 业务可复用组件 | - | 业务实现 |
| `core/` | 应用配置/容器/生命周期 | - | 业务代码 |
| `database/` | DB/Redis/Cache 基础设施 | core | 业务逻辑 |
| `middleware/` | HTTP/安全/可观测性中间件 | common, core | 业务路由 |
| `utils/` | 纯函数工具 | - | 业务逻辑 |

### 3.3 依赖方向 (单向, 严格禁止反向)

```
app/      ──┐
            ├──>  common/, core/, database/, middleware/, utils/
plugin/   ──┤
workers/  ──┘  (workers/ 仅依赖 app/*/service)

common/   ──>  (无依赖, 叶子节点)
core/     ──>  (无依赖, 叶子节点)
database/ ──>  core/, common/
middleware/──> core/, common/, utils/
utils/    ──>  (无依赖, 叶子节点)
```

**禁止依赖**:
- ❌ `common/` → `app/` (common 不能依赖业务)
- ❌ `core/` → `app/` (core 不能依赖业务)
- ❌ `database/` → `app/` (database 不能依赖业务)
- ❌ `utils/` → 任何上层 (utils 必须是纯函数)
- ❌ `app/admin/` → `app/tasks/` (应用间不直接 import, 通过 EventBus)

## 四、关键设计模式 (Key Design Patterns)

### 4.1 应用注册中心 (app/registry.py)

```python
# common/interfaces.py
from abc import ABC, abstractmethod
from fastapi import APIRouter

class AppInterface(ABC):
    """所有业务应用必须实现的接口"""
    
    @property
    @abstractmethod
    def name(self) -> str: ...  # "admin" / "tasks" / "annotation"
    
    @property
    @abstractmethod
    def version(self) -> str: ...  # "1.0.0"
    
    @property
    @abstractmethod
    def router(self) -> APIRouter: ...
    
    @abstractmethod
    def register_events(self) -> list: ...  # 订阅领域事件
    
    @abstractmethod
    async def startup(self): ...  # 应用启动钩子
    
    @abstractmethod
    async def shutdown(self): ...  # 应用关闭钩子

# app/registry.py
class AppRegistry:
    _apps: dict[str, AppInterface] = {}
    
    @classmethod
    def register(cls, app: AppInterface):
        cls._apps[app.name] = app
    
    @classmethod
    def all_routers(cls) -> list[APIRouter]:
        return [app.router for app in cls._apps.values()]
    
    @classmethod
    async def startup_all(cls): ...
    @classmethod
    async def shutdown_all(cls): ...

# app/tasks/__init__.py
class TasksApp(AppInterface):
    @property
    def name(self) -> str: return "tasks"
    @property
    def version(self) -> str: return "2.0.0"
    @property
    def router(self) -> APIRouter:
        from app.tasks.api import router
        return router
    def register_events(self): return []
    async def startup(self): ...
    async def shutdown(self): ...

AppRegistry.register(TasksApp())
```

### 4.2 插件注册中心 (plugin/registry.py)

```python
# common/interfaces.py
class PluginInterface(ABC):
    """所有插件必须实现的接口"""
    
    @property
    @abstractmethod
    def name(self) -> str: ...  # "minio_storage" / "yolov8_backend"
    
    @property
    @abstractmethod
    def version(self) -> str: ...
    
    @abstractmethod
    def install(self, app_registry: AppRegistry) -> None:
        """插件安装: 注册路由/事件/服务到目标 app"""
    
    @abstractmethod
    def uninstall(self) -> None: ...

# plugin/storage_backends/__init__.py
class MinioStoragePlugin(PluginInterface):
    def install(self, app_registry: AppRegistry):
        # 注册到 tasks app, 提供文件存储能力
        from app.tasks.service.file_storage import set_storage_backend
        set_storage_backend(MinioBackend())

# 在 main.py 启动时加载
def load_plugins():
    PluginRegistry.register(MinioStoragePlugin())
    PluginRegistry.register(YoloDetectionPlugin())
```

### 4.3 领域事件总线 (common/events.py)

```python
# common/events.py
from dataclasses import dataclass
from datetime import datetime
from typing import Callable, Awaitable
import asyncio

@dataclass
class DomainEvent:
    name: str  # "task.started" / "user.created" / "image.annotated"
    payload: dict
    occurred_at: datetime = None

class EventBus:
    """跨应用/插件通信总线"""
    _handlers: dict[str, list[Callable[..., Awaitable[None]]]] = {}
    
    @classmethod
    async def publish(cls, event: DomainEvent):
        for handler in cls._handlers.get(event.name, []):
            asyncio.create_task(handler(event))
    
    @classmethod
    def subscribe(cls, event_name: str, handler: Callable):
        cls._handlers.setdefault(event_name, []).append(handler)

# app/tasks/events.py
@EventBus.subscribe("user.created")
async def on_user_created(event: DomainEvent):
    """新用户创建 → 初始化默认数据集"""
    user_id = event.payload["user_id"]
    await create_default_dataset(user_id)

# app/admin/events.py
async def create_user(self, ...):
    user = await self.user_repo.create(...)
    await EventBus.publish(DomainEvent(
        name="user.created",
        payload={"user_id": user.id}
    ))
```

### 5.1 `app/` 业务应用 (核心)

## 七、性能优化 (Performance)

### 7.1 当前性能瓶颈

| 瓶颈 | 影响 | 解决方案 |
|---|---|---|
| 训练启动延迟 | 用户体验 | 异步预创建 + Redis 缓存 |
| 图像上传大文件 | 超时 | 流式上传 (FastAPI UploadFile) |
| 数据库连接池 | 串行 | 读写分离 + pool_size 调优 |
| Redis 无抽象 | 难以扩展 | `CacheInterface` 抽象 |
| ML 推理串行 | 慢 | 批处理 + Celery 异步 |

### 7.2 关键性能优化

#### 优化 1: 读写分离 (database/engine.py)
```python
class Database:
    write_engine: AsyncEngine  # 主库
    read_engine: AsyncEngine   # 从库 (可同主库)

def get_write_db(): ...  # 写
def get_read_db(): ...   # 读
```

#### 优化 2: 缓存层 (database/cache.py)
```python
class CacheInterface(ABC):
    @abstractmethod
    async def get(self, key: str) -> Any: ...
    @abstractmethod
    async def set(self, key: str, value: Any, ttl: int = 300): ...

@cache.cached(key_pattern="dataset:{id}:stats", ttl=60)
async def get_dataset_stats(id: int): ...
```

#### 优化 3: 应用启动顺序优化 (core/lifespan.py)
```python
async def lifespan(app):
    # 1. 数据库
    await init_db()
    # 2. Redis
    await redis_client.connect()
    # 3. 应用启动 (按依赖顺序)
    for app in AppRegistry.all_apps():
        await app.startup()
    # 4. 插件加载
    PluginRegistry.install_all()
```

#### 优化 4: 慢请求监控 (middleware/http/timing.py)
```python
@app.middleware("http")
async def timing_middleware(request, call_next):
    start = time.time()
    response = await call_next(request)
    duration = time.time() - start
    if duration > 1.0:  # 1s 慢请求
        logger.warning(f"Slow request: {request.url.path} took {duration:.2f}s")
    return response
```

## 十一、决策记录 (Decision Records)

### DR-1: 为什么 app/ 顶层放业务应用而不是 3 层?
**决策**: ✅ 采用 app/ 顶层
**理由**: 多应用隔离, 团队协作友好, 易于未来拆分微服务
**对比**: 3 层架构 (api/service/model) 让应用间界限模糊

### DR-2: 为什么 plugin/ 与 app/ 平级?
**决策**: ✅ 平级
**理由**: 强调插件的"独立性" - 可被多个 app 复用, 升级不依赖 app
**对比**: 把 plugin 放 app 内会让插件升级被迫跟随 app 节奏

### DR-3: 为什么 common/ core/ database/ middleware/ utils/ 5 个目录?
**决策**: ✅ 5 个独立目录
**理由**: 关注点彻底分离 - 业务组件 / 应用配置 / 数据 / 中间件 / 工具 各司其职
**对比**: 合并到 1-2 个 `shared/` `infrastructure/` 会让职责变模糊

### DR-4: ORM 模型归属: app 内 vs database 顶层?
**决策**: ✅ ORM 放 app/{domain}/model/
**理由**: ORM 模型强耦合业务 (字段含义/关系由业务决定), 放 database 会让 database 依赖业务
**对比**: database 顶层只放基础设施 (engine/base/session/migrations), 不放业务模型

### DR-5: 是否引入 DI 容器?
**决策**: ✅ 引入 (Stage 5)
**理由**: 显式管理依赖, 便于单测; 替代散落 Depends
**风险**: 学习成本, 但收益明显

### DR-6: 是否引入事件总线?
**决策**: ✅ 引入 (Stage 5)
**理由**: 解耦 app 间通信, 避免直接 import
**风险**: 调试链路变长, 但 logging/tracing 配套缓解

### DR-7: 是否用 Alembic 替代现有 db_migration.py?
**决策**: ✅ Stage 3 升级到 Alembic
**理由**: 行业标准, 社区成熟, 自动生成迁移
**过渡**: 保留 `init_db()` 兜底, 灰度切换

### DR-8: ML 框架是否从 app 内部移到 plugin?
**决策**: ✅ 移到 plugin/ml_backends
**理由**: 强化可插拔性, 未来支持多框架 (MMDet/Detectron2) 是后续可拓展方向
**权衡**: 增加一层抽象, 但 Stage 4 独立可做
