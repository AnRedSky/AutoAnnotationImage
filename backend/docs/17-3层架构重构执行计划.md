# 后端 3 层架构重构执行计划

## 一、摘要 (Summary)

将现有后端 (\~12,700 行 / 66 个 Python 文件) 按 **3 层架构 (API / Service / Data) + 5 个支撑目录 (schemas / common / utils / core / middleware)** 重组, 实现清晰关注点分离。重构过程保证 HTTP 协议、Celery 任务、数据库 schema、配置、启动命令 5 项完全不变。

**核心问题** (基于 2026-07-24 代码库实际探索):

* `api/training.py` 1151 行 / `api/image.py` 1096 行 / `api/detection.py` 889 行 — 路由层混入业务编排、DB 查询、Celery 派发、状态机

* `services/` 仅 3 个文件 (ai/bbox/storage), 13 个业务域缺 Service 层

* `core/` 混合 6 类关注点 (config/security/deps/celery\_utils/exceptions/redis\_client)

* 跨层直接调用: api→workers 7 处, api→ml 4 处, workers→ml/models 28 处

* import 迁移规模大: `app.models` 129 处, `app.database` 44 处, `app.config` 25 处

## 四、假设与决策 (Assumptions & Decisions)

### 4.1 已确认决策 (沿用前期 AskUserQuestion 结论)

1. **范围**: 目录重组 + SoC 抽取 (10-12 天), 非 Clean Architecture/Repository 接口
2. **workers/ml**: 保留顶层 (`app/workers/`, `app/ml/`), 不下沉
3. **model/ 风格**: ORM 模型 + 查询函数 (Active Record + `*_queries.py`), 不抽象 Repository 接口
4. **迁移方式**: 分阶段迁移, 每阶段可独立验证

### 4.2 关键技术决策

| 决策点                      | 选择                                      | 理由                                       |
| ------------------------ | --------------------------------------- | ---------------------------------------- |
| `models/` → `model/` 重命名 | 整体重命名 + 全量 import 更新                    | 与用户要求 `model/` 一致                        |
| Base 类位置                 | `app/model/base.py`                     | 数据层关注点, 与 ORM 同目录                        |
| 兼容垫片                     | **采用** (迁移期临时保留旧路径转发)                   | 129 处 `app.models` 引用, 一次性改易出错; 垫片保证渐进迁移 |
| Service 注入方式             | FastAPI `Depends(get_xxx_service)` 工厂函数 | 与现有 `get_db`/`get_current_user` 风格一致     |
| 状态机统一                    | `JobStateService` 单一入口                  | 解决 4 处真相源 (Celery/DB/Redis/前端)           |
| Celery 任务兼容              | task name + 入参严格不变                      | 避免已入队任务丢失                                |

### 4.3 硬约束 (来自 project\_memory, 必须遵守)

* `model/dataset` 级联删除必须手动按序: training\_job → model\_version → annotation\_log → image → category + 磁盘清理 (MySQL 仅 category/image 有 CASCADE)

* Celery `run_training` 返回值必须 JSON 可序列化 (ndarray→list, float64→float, int64→int)

* `/api/training/progress/{task_id}` 必须 DB 兜底 (Celery SUCCESS 时 `info` 是返回值非 meta)

* 训练 `train_cb`/`epoch_cb` 必须同时写 Redis `history_buffer` 和 DB `TrainingJob.history`

* Windows 进程创建仅用 `DETACHED_PROCESS (0x8)`, 不可混用 `CREATE_NEW_CONSOLE`

* 前端启动命令须 `cmd /c npm run dev` 包装

```python
    def __init__(self, db: AsyncSession):

        self.redis = redis_client

    async def on_start(self, task_id: str, job_id: int, total_epochs: int) -> None:
        # 写 Celery current_task.update_state(state="PROGRESS")
        # 写 DB TrainingJob.state="PROGRESS", started_at=utcnow()
        # 写 Redis history_buffer = []

    async def on_progress(self, task_id: str, progress: int, message: str = "") -> None:
        # 写 Celery update_state + DB TrainingJob.progress/message

    async def on_epoch(self, task_id: str, job_id: int, metrics: dict) -> None:
        # 写 Redis history_buffer (LPUSH/append)
        # 写 DB TrainingJob.history (JSON append)
        # 写 Celery update_state (含 progress)

    async def on_success(self, task_id: str, job_id: int, result: dict) -> None:
        # 写 Celery state=SUCCESS (result 必须 JSON 可序列化: ndarray→list, float64→float)
        # 写 DB TrainingJob.state=SUCCESS, progress=100, finished_at=utcnow()

    async def on_failure(self, task_id: str, job_id: int, error: str) -> None:
        # 写 Celery state=FAILURE
        # 写 DB TrainingJob.state=FAILURE, message=error, finished_at=utcnow()
```

**关键约束** (project\_memory):

* `on_success` 的 result 必须 JSON 可序列化 (Celery `mark_as_done` 会 `kombu.dumps`)

* `on_epoch` 必须同时写 Redis 和 DB history
