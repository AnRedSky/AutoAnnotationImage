## 二、关键决策与权衡

### 2.1 P0-1 `BBoxAnnotation.model_name` 字段处理

- **决策**: 删除 ORM 字段，模型名改存到 `AnnotationLog.payload` (JSON)
- **权衡**:
  - ✅ 避免 migration 复杂度（不需要 add/drop column）
  - ✅ payload 字段通用性更强，未来其他审计信息也可存
  - ✅ BBoxAnnotation 表 schema 不变，向后兼容
  - ❌ 查询"哪些 box 来自哪个模型"需要 JOIN AnnotationLog
- **影响**: BBoxAnnotation 表结构无变化，审计信息无丢失

### 2.2 P0-2 `AnnotationLog.action` 枚举扩展

- **决策**: 新增 2 个枚举值 `auto_annotate_pretrained` / `auto_annotate_finetuned`，并新增 `payload` JSON 字段
- **权衡**:
  - ✅ 区分两种 auto-annotate 场景（预训练 vs 已训练），审计可追溯
  - ✅ payload 字段为后续扩展留空间（不需每次扩 Enum）
  - ❌ 既有数据保留（无破坏性变更），但需要 alembic 迁移
- **迁移脚本**: `backend/migrations/extend_annotation_log_enum.py` (幂等)

### 2.3 P0-3 celery include 修复

- **决策**: `include` 列表追加 `app.workers.segmentation_tasks`
- **权衡**: 一行配置修复，避免 NotRegistered 运行时错误
- **预防**: 未来新增 worker 模块需同步更新 `include` 列表（已在 v2.5.15 commit message 提示）

### 2.4 P0-4 `start_training` 异步化

- **决策**: `def → async def`，删除 `_run_async` 嵌套；socket 操作走 `asyncio.to_thread`
- **权衡**:
  - ✅ FastAPI 异步生态一致性
  - ✅ 不再依赖 Celery worker 同步调用栈
  - ✅ socket 操作（同步 IO）通过 `to_thread` 移交线程池，不阻塞事件循环
- **影响**: API 响应不再阻塞，可与数据库 IO 并发

### 2.5 P1-1/2 SECRET_KEY + MYSQL_PASSWORD 生产 fail-fast

- **决策**: `model_validator` 在生产环境抛 `ValueError`；开发环境 `warnings.warn`
- **权衡**:
  - ✅ 生产 fail-fast：阻止弱密钥/默认密码上生产
  - ✅ 开发友好：本地开发仍可用默认值（仅警告）
  - ✅ 零误伤：失败信息明确，便于排查
- **默认值调整**: `MYSQL_PASSWORD` 默认值由 `"root123"` 改为 `""`，强制显式配置

### 2.6 P1-3 CORS '*' + credentials 互斥自动降级

- **决策**: 生产强制白名单（`'*'` 直接 `RuntimeError`）；开发自动降级 `credentials=False`
- **权衡**:
  - ✅ 生产安全：杜绝 CORS 跨域携带 cookie 风险
  - ✅ 开发体验：本地 dev 自动降级，无需手动配置
  - ✅ 符合浏览器 CORS 规范（W3C Fetch spec）
- **生产指引**: `CORS_ORIGINS=https://app.example.com,https://admin.example.com`

### 2.7 P1-4 线程池大小

- **决策**: `cpu_count * 2`，上限 16
- **权衡**:
  - ✅ CPU 模式 sweet spot：与 PyTorch 推荐的 inter-op threads 一致
  - ✅ 避免过大 context switch 开销
  - ✅ GPU 模式自动收敛到 CPU 数（GPU 推理主要受显存而非 CPU 限制）
- **计算**: `_workers = max(2, min(16, _cpu * 2))`

### 2.8 P1-5 ModelPool 设计

- **决策**: `OrderedDict` 实现 LRU + `threading.Lock`，`max_size=2`
- **权衡**:
  - ✅ 预训练 + fine-tuned 双 model 是主流场景，max_size=2 完全覆盖
  - ✅ LRU 策略：长期不用的模型自动淘汰，避免内存无限增长
  - ✅ 锁粒度：每次 get_or_load 一次性加锁，避免 check-then-act 竞态
- **扩展性**: 后续可暴露 `hits` / `misses` 计数到 `/metrics` 端点（v2.6.0 计划）

### 2.9 P1-6 真批处理实现

- **决策**: `torch.stack` 拼 batch，默认 `batch_size=8`
- **权衡**:
  - ✅ CPU 模式内存 sweet spot：8 张 320x320 RGB ≈ 8 * 320*320*3*4B = ~10MB
  - ✅ 大图场景可降到 4，避免 OOM
  - ❌ 与单图推理兼容性差（接口签名已变更，需 `_batch_predict_sync` 内部重写）
- **接口设计**: 保留 `predict_image(image_path)` 兼容单图，自动走 batch 路径

## 九、经验教训

1. **mock 是双刃剑**: `MagicMock.__len__` 默认返回 0，导致 `len(r.boxes) == 0` 跳过整个 image（YOLO mock 必须显式 `__len__.return_value`）
2. **StaticPool 内存库**: `:memory:` 模式下必须用 StaticPool + 共享连接，否则多 AsyncSession 看不到表
3. **`grad_fn` 缺失**: mock `nn.Module` forward 用纯 `torch.zeros` 会缺 `grad_fn`，必须经过 `nn.Conv2d` 等可学习层
4. **Eager 模式副作用**: `task_always_eager=True` 会污染全局 celery_app.conf，fixture 必须 try-finally 恢复
5. **enum 扩展代价**: MySQL ALTER ENUM 风险（数据截断），需先 SELECT 现有值再扩展
6. **`include` 列表**: Celery worker 启动时静默，未注册的 task 调 `.delay()` 才报错 → 必须有测试覆盖
