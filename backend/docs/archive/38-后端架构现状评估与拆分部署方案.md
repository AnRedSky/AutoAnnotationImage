## 二、架构评估：从 5 个维度

### D1. 部署拓扑

**现状判断**：✅ 合适。

理由：
- **API 与 Worker 进程边界正确**。`api` (`uvicorn`) 与 `worker-*` (`celery -A`) 是**两个完全不同的运行时**——共用一套 Python 代码但不共享 GIL/事件循环。CPU bound 的训练任务会阻塞 uvicorn event loop，所以分进程是**必要的**，不是装饰性的。
- **不同 Worker 分容器** (`worker-train` 1 并发 / `worker-annotate` 4 并发) **有明确资源语义**。train 任务内存峰值可达数 GB（YOLOv8 / DeepLabV3+）+ 可能独占显存；annotate 任务百 MB 级。混部会互相 OOM。这套配置**已经反映了物理现实**。
- **依赖图清晰**。`api` 不依赖 `worker` 可启动（虽然业务上 worker 不可用 = 训练接口挂掉），但反向 (`worker` 依赖 `api`) 没有强耦合——`api` 仅作为 worker 注册中心的命名锚点。
- **共享镜像 + 差异化 CMD** 是最经济的——`Dockerfile.worker FROM base` 一层共享，二进制零冗余。

**反向用例**：
- 单 dev 本地跑：`docker compose up api mysql redis minio` 一条命令启动，比原来 `start_api.py + start_workers.py + 本地 Redis.exe` 还简单 → ✅
- 反向用例没破：worker 不需要也照样能起 api（用户能登录、上传、调非训练路由）。

**潜在风险点**（非阻塞）：
- worker-train 容器现在 `concurrency=1` 没做 GPU 抢占控制——一旦真有 GPU 部署，需要 `NVIDIA_VISIBLE_DEVICES` 调度。
- `app/database` 里 `engine` 是进程级单例——API 进程与 Worker 进程是各自独立的连接池；但如果将来加多 API 副本与多 Worker 副本，要注意 DB pool size 累加不能超 DB max_connections。

### D2. 资源隔离

**现状判断**：✅ 合适。

证据：
- 任务的**资源画像**在 `celery_app.task_routes` 上已经做了**显式分类**：`train = CPU/GPU bound, concurrency=1` / `annotate = I/O bound, concurrency=4`。
- 这是**有意识的设计**——见 `celery_app.py` 注释 "v3.1.0 Phase W2.2: 训练任务路由到独立队列, 避免 CPU 密集训练与 I/O 标注互踩"。

反向用例：
- `task_time_limit=3600s` 对 100 张图以内的训练任务够用；对 10k 张数据集级别训练要砍半或提供 SSE 增量进度，否则 worker 看起来"卡死"。

**潜在风险点**：
- ML 推理服务没有独立进程。当前**推理（单图 / 批量）走 API 进程的 `ai_service.current_model`**。**这是真正的瓶颈**——文档 `docs/04-性能优化与监控建议.md` 已经记录 "全局单例模型多任务互踩"。
  - **判断**：这不是部署架构问题，是**应用架构问题**。结论：API 内推理应改为**模型池**（`ModelPool` 类已存在但只是占位），见 §四 P1。

### D3. 可观测性

**现状判断**：⚠️ 基本够，但**故障场景的链路追踪是真实的缺口**。

证据：
- `/api/health` 把三个外部依赖都探了一遍（DB ping + Redis ping + MinIO HTTP live）——这是 best practice。
- `/api/metrics` 有进程级资源 + DB pool stats + cache hit/miss + 慢 SQL。
- 每个业务域都有 SSE 流式进度接口。

缺口：
- **没有 worker 进程自身的 metrics**（活跃任务数、队列长度、平均任务时长）。需要 worker 暴露 `/metrics` 端点（Celery Prometheus exporter `celery-exporter`），或在 health/metrics 端点上聚合 worker 侧状态。
- **没有跨 API/Worker 的 trace_id 关联**。当 SSE 流推到一半断了，用户报错 "进度卡 99%" 时，没有任何 trace_id 能串联起 API 收到的 revoke 请求、Worker 收到的 SIGTERM、TrainingJob 写入的状态变更。
- **model auto-annotate / training 失败时没有死信队列**（DLQ）。失败的 `auto_annotate_*` 任务直接丢，UI 通过 `task_id` 轮询发现 `FAILURE`，但失败原因散落在 celery.log 中。

### D4. 失败模式

**现状**：**已经过几次实战检验**（commit log 显示 v3.0.0 Phase N/O/P/Q/R/S 多次 "fix(workers)" "fix(backend)"）。最严重的失败模式都有处理：

| 失败模式 | 当前行为 | 是否合适 |
|---|---|---|
| Redis 不可用 | `broker_connection_max_retries=2`，快速失败 + `/api/health` 立刻红 | ✅ |
| MySQL 不可用 | API 返回 500；health 红；Worker 任务 retry 一次后落 FAILURE | ✅ |
| Worker 崩溃 | API 提交的任务 PENDING → STARTED 不变；超时（visibility_timeout=3600s）后会被 re-deliver | ⚠️ 3600s 太长，等于这个时间窗口内的失败任务不可见 |
| MinIO 不可用 | `export_*` 系列端点会 500 | ⚠️ 没有专门的端点提示 "是不是 MinIO 挂了" |
| 模型 checkpoint 损坏 | 训练 task 抛异常，state=FAILURE，UI 拿到 err_msg | ✅ |
| 训练过程中 Worker 重启 | visibility_timeout=3600s 兜底，但用户看到的进度会被 re-deliver 重置 | ⚠️ 长任务 + SIGTERM 联动的恢复策略没有详细设计 |
| 任务超时（>1h） | `task_time_limit=3600s` 触发，整个 task 被杀 | ⚠️ 没有 chunked-training，部分推理结果会丢失 |
| 队列堆积 | 没有监控 | ⚠️ 缺口 |
| Worker 进程 OOM | 容器 OOM kill，进程级 PID 消失 | ⚠️ 缺少 worker 自身 metrics，无法预警 |

### D5. 工程经济学

**判断**：**当前对单 dev / 10 人团队正好**；**对百级并发的 SaaS 化不够**。

| 场景 | 当前够用？ | 关键瓶颈 |
|---|---|---|
| 单 dev，本地全栈 | ✅ | 无 |
| 5–10 人小团队，单机 compose | ✅ | 无 |
| 50–100 并发用户（含 SSE 流） | ⚠️ | uvicorn worker 数=1；DB pool 10+20 |
| 1000+ 并发用户 | ❌ | 必须先解决：推理不在 worker、模型池缺位、cache 层热路径未覆盖 |
| 多 region / K8s 化 | ❌ | compose 文件仍是单假设，需重写 deploy/k8s/helm |

## 三、当前拆分部署方案评估

### 核心判断：**当前合适**

适用条件：
- 单 dev / 小团队协作
- 单机 / 单 VM 部署
- CPU 训练（不是 GPU K8s 化）
- 用户量级 ≤ 100 并发

**适用条件之外，必须做的下一步**：
- 进 K8s：把 `compose.yaml` 拆分为 helm chart 或 kustomize；扩缩容由 HPA 而非手工 docker-compose scale 驱动
- 进大用户量：API → uvicorn 多 worker + 推理服务独立 + 模型池 + Redis 缓存层
- 进 GPU 集群：`worker-train` 容器加 GPU 调度 + checkpoint 持久卷 + 队列优先级

### 这个方案"为什么"合适（值得未来人记住的 3 条原则）

1. **业务边界 = 资源边界**。train / annotate 分容器不是装饰，是数据观察到的——训练任务内存峰值 4-8GB vs 标注任务百 MB 级。如果未来新增一类资源画像强差的任务（如视频流推理），应单独新开 worker，不要在 train 上挂。
2. **API 与 Worker 是同一份代码的两个运行时**。它们共享同一 `uv.lock`，但**进程边界要永远保留**。一旦把 Worker 内嵌到 API 进程（用 background thread 假装 worker），CPU bound 任务会阻塞事件循环，2 分钟内整个 API 不可用。
3. **可观测性的最低门槛已经达成**——再低的部署形态没有 `/api/health` 是不行的。这条已经做到了。

~~`ai_service.batch_predict` 批处理是"假"批处理~~

复审：`_batch_predict_sync` 已用 `torch.stack(tensors[start:start + batch_size]).to(device)` 一次性 forward、`topk(dim=1)` 全 batch 返回。注释明确写 **"真批处理"**，与代码一致。**本条作废**。

#### P0-1（修正后）Worker SIGTERM handler 缺失

- **问题**：`app/tasks/api/training/jobs.py:148` 已经 `revoke(terminate=True, signal="SIGTERM")`，但 `grep -r SIGTERM app/tasks/workers/` **0 命中**——worker 进程收到 SIGTERM 走 Python 默认处理（直接退出），不写 checkpoint、不优雅收尾。
  - 后果：长训练任务（数小时）取消时已经加载进内存的 dataset、模型 checkpoint 丢失；任务标记为 REVOKED 但 broker 端 task 仍在 WORKER_PROGRESS 上报，可能产生 race。
- **怎么做**：
  - 在 `app/tasks/workers/celery_app.py` 注册 worker_process_init signal hook 或在 worker_main argv 加 `--task-events`
  - 写一个 `signal_handlers.py`（在 `app/tasks/workers/` 下）注册 `SIGTERM` 行为：调用 ultralytics/torch 的保存钩子 + 把 `train_emergency:{task_id}` 写 Redis
  - 在每个 long-running 任务（train_model_task, train_detection_task, train_segmentation_task）入口注册 process-level 的 `atexit` + signal handler
  - **RED 测试**：发起一个 `train_model_task` mock 注入 sleep，调用 cancel 后 ≤5s 内 (a) `train_emergency:{task_id}` 在 Redis 中存在 (b) TrainingJob 表里有 emergency checkpoint path 写入。
- **风险**：handler 内 try/except 必须够厚（任务正常完成时仍要走原 cleanup 路径）；signal 不能在 `await` 上下文里跑，只能 set flag 暴露给主循环。
- **不做的代价**：用户在大数据集训练 30 分钟后想停，停不下，需要等到 `task_time_limit=3600s` 自然超时——等同于反馈失灵。

#### P0-2（重新编号）`/api/health` 在 DB 挂掉时仍 200

- **当前行为**（实证：`inspect.getsource(health_check)` 后 `5xx raised? False, degraded set? True`）：`app/admin/api/system.py:48` 写入 `result["status"] = "degraded"`，但**HTTP 状态码始终 200**——`/api/health` 不抛 `HTTPException(503)`。
- **影响**：compose 的 healthcheck 是 `curl -fsS http://...api/health`——`fsS` 看 HTTP code 一定是 200。**K8s readiness probe / 阿里云 SLB 都会路由流量到 DB 已挂的实例**。
- **怎么做**：
  - `health_check` 改返回签名：当 DB (`result["checks"]["database"]["ok"] is False`) 时抛 `HTTPException(status_code=503, detail=result)`，让 503 真正发出。
  - Redis / MinIO 失败可以降级为 degraded 而非 503——它们可以走 fastapi `cache` fallback（`CACHE_ENABLED=False`）。
  - **RED 测试**：mock `db.execute` 抛异常 → 客户端拿 503；Redis 异常 → 客户端拿 200 但 status=degraded。
- **不做的代价**：未来从 compose 迁到 K8s 时，第一次发布就该问题引爆——凌晨 4 点 PagerDuty 全响。

### P1 — 短期，3 个月内

- **P1-1 模型池化**（`ModelPool` 类已存在但只是 dict）：把模型按 task_type + model_name 缓存，避免多模型切换时全加载/卸载。
- **P1-2 Worker metrics**：`celery-exporter` 暴露 worker 侧 prometheus 端点，docker-compose 加一个 `worker-metrics` 容器，或在每个 worker 容器暴露 `localhost:9001/metrics`。
- **P1-3 Cross-process trace_id**：API 收到请求 → 通过 Redis 写 `task:meta:trace_id` → Worker 启动时取 → 日志格式统一带 trace_id。
- **P1-4 任务超时分级**：单任务 > 1h 拆 chunked（用户级训练集 <=1k 张 → 1h 上限；>1k 张 → 评估是否走 checkpoint-resume）。

### P2 — 中期，6 个月+

- **P2-1 K8s 化**：compose → helm/kustomize，扩缩容 HPA 化，GPU 时间片 (`time-slicing`) 配置
- **P2-2 推理服务独立化**：`model-server` 新进程（独立 Docker image，类似 Triton），API 通过 HTTP 调
- **P2-3 模型版本与训练松绑**：TrainingJob 物理删，但 model_version 不删，提供"训练历史归档"端点
- **P2-4 DLQ 与重试策略分级**：失败任务进入 DLQ 表，5xx/网络错自动重试 1 次；OOM/校验错直接 FAILURE

## 五、当前拆分部署架构方案（基线快照）

> 到 2026-07-30 为止，**已落地**的拆分部署架构，作为未来 rebase/重构的基线。

### 文件清单

```
backend/
├── Dockerfile           # base stage (uv sync + 项目本体)
├── Dockerfile.api       # uvicorn app.main:app
├── Dockerfile.worker    # celery -A app.tasks.workers.celery_app
├── .dockerignore        # 镜像构建白名单
├── .env.docker          # 容器内统一 env (服务名: mysql/redis/minio)
├── pyproject.toml       # 依赖真实源
├── uv.lock              # 139 包锁定
└── console_scripts:
    api                  # uvicorn
    worker               # celery (合并 train+annotate)
    worker-train         # celery -Q train -c 1
    worker-annotate      # celery -Q annotate -c 4
    healthcheck          # py_compile 全扫描

docker-compose.yml        # 7 services: mysql/redis/minio/api/worker-train/worker-annotate/frontend
```

### 编排约束

| 约束 | 原因 |
|---|---|
| worker 容器不暴露端口 | 防御性——避免被外部 HTTP 调 |
| api 用 `--proxy-headers --forwarded-allow-ips="*"` | 给前置 LB 用 |
| 三个 worker 共享 `Dockerfile.worker` 镜像 | 减少镜像体积；用 CMD 差异 |
| `depends_on` 用 `condition: service_healthy` | 启动顺序可预期 |
| `restart: unless-stopped` | 临时崩溃自动恢复 |
| `api_logs:/app/logs` 命名卷 | 跨容器日志可被 host 收集 |

### 这套方案 vs 历史版本对比

| 维度 | 拆分前（v2.5.x 单镜像） | 拆分后（v3.1.0+ 三镜像） | 影响 |
|---|---|---|---|
| 进程镜像 | 1 (uvicorn + celery 同进程) | 3 (api / worker-train / worker-annotate) | 训练不再阻塞 HTTP |
| 扩缩容维度 | 整体 | 维度：API 副本数 / train worker 数 / annotate worker 数 | 灵活 |
| 依赖图 | uv.lock 1 份 | uv.lock 1 份（共享） | 零浪费 |
| CPU 训练互踩 | 经常 | 不会（不同容器） | 体感 |
| 配置复杂度 | 1 份 .env | .env.example + .env.docker | 中等，可控 |

## 六、下次重新评估的触发条件

> 未来任何人想重新评估这个架构，应该在发生以下任意一项时启动。**不要等季度评审才看**——条件 = 信号。

| 触发条件 | 信号 | 行动 |
|---|---|---|
| 用户量 10× | `/api/health` 出现过连续 3 分钟 CPU > 70% | 重读 §二 D5，重做 P1-1/3 |
| 训练任务超时变日常 | 任何训练任务在 logs 中 `task_time_limit` 出现 ≥ 1 次/天 | 启动 P1-4 chunked-training |

| 服务崩溃无人发现 | 因为健康检查 200 但内部 broken | 推进 P0-3 + 引入 Sentry/OpenTelemetry |
