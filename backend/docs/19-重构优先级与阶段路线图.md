## 二、阶段衔接与依赖关系

```
Phase 1 (基础设施) ✅
    ↓ 提供干净的目录骨架
Phase 2 (Data 层)
    ↓ 让 ORM 更内聚, 查询函数可复用
Phase 3 (Service 层)
    ↓ 让业务规则有家, 路由可以薄
Phase 4 (API 薄化 + Schema)
    ↓ API 文件 < 300 行
Phase 5 (Worker 薄化)
    ↓ workers 委托 service, ml 纯计算
    ↓ (可选) Stage 2-5: 多应用拆分
```

**关键依赖**:
- Phase 2 强依赖 Phase 1 (model/ 目录已就位)
- Phase 3 强依赖 Phase 2 (需要 ORM 加业务方法)
- Phase 4 强依赖 Phase 3 (Service 抽取后才能薄化路由)
- Phase 5 弱依赖 Phase 3 (Worker 也可以直接调 model, 但调 service 更优)

## 四、Phase 2 计划 (待开始)

### 目标
1. `app/models/` → `app/model/` 重命名 (9 个 ORM 文件)
2. 129 处 `from app.models import` 全量更新
3. 给每个 ORM 加 Active Record 业务方法:
   - `TrainingJob.is_terminal() / transition_to()`
   - `ModelVersion.activate() / deactivate()`
   - `Dataset.cascade_delete()` (业务规则)
   - `Image.set_status()`
   - `BBoxAnnotation.compute_area()`
4. 抽取 9 个 `*_queries.py` 查询函数文件
5. 删除 Phase 1 兼容垫片 (8 个)

### 关键决策
- **强制原则**: ORM 不依赖 Service, Service 不依赖 API
- **增量策略**: 每个 ORM 文件单独迁移 + 验证
- **回滚方案**: 兼容垫片保留至 Phase 2 收尾时删除

### 验收标准
- 所有现有 99 个路由行为不变
- 单元测试 100% 通过
- `py_compile` 全量通过
- `app.models` 全部替换为 `app.model`
- ORM 业务方法覆盖率 > 80% (至少 8 个核心业务规则方法)

### 风险与缓解
| 风险 | 缓解 |
|---|---|
| 129 处 import 漏改 | 自动化脚本: `python -m py_replace app.models app.model --include '*.py'` |
| ORM 加方法破坏现有逻辑 | 业务方法命名遵循 `is_xxx` / `transition_to_xxx` / `mark_xxx`, 不改变已有行为 |
| 兼容垫片删除遗漏 | 阶段收尾时 `grep -r "from app\.\(models\|config\|cli\|database\)$" backend/app/` 应为空 |

## 八、阶段验收与提交流程

每阶段完成后:

1. **代码自检**:
   ```bash
   cd backend
   python -m py_compile app/**/*.py
   python -c "import app.main; assert len(app.main.app.routes) >= 99"
   ```

2. **测试**:
   ```bash
   cd backend
   pytest tests/ -v --tb=short
   ```

3. **写完成报告**: 在 `backend/docs/` 下新增 `XX-PhaseN-实施完成报告.md`

4. **更新本路线图**: 标记当前 Phase 为 ✅, 更新下一阶段目标

5. **Git 提交**:
   ```bash
   git add backend/
   git commit -m "refactor(phaseN): <简短描述>"
   ```

6. **立即推进下一阶段**: 不等待用户指令, 按路线图自动衔接
