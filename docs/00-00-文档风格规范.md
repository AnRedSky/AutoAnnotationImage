# 文档风格规范

> **版本**: v1.3
> **生效日期**: 2026-08-13
> **适用范围**: `docs/`、`backend/docs/`、`frontend/docs/`、`deploy/docs/` 下所有 Markdown 文档
> **维护人**: 项目全体开发与文档维护人员

本规范定义项目内部技术文档的写作要求。规范面向项目交付物本身，目的是让所有技术文档保持一致、可执行、易维护。

---

## 一、文档定位

本项目所有 `*.md` 文档均为**工程交付文档**，服务于：

- 工程师快速理解模块职责、接口契约、配置项、操作步骤
- 运维人员按文档完成部署、监控、故障恢复
- 新成员按文档完成环境搭建与首次使用
- 记录实现决策、变更历史、已知问题

文档不承载以下内容：

- 学术体例（封面、摘要、关键词、致谢等）
- 学术引用格式与文献综述
- 研究性论述、理论探讨
- 任何非项目本身所需的修辞

## 二、风格总则

### 2.1 直接陈述事实

- 用"是什么"代替"为了实现……，本文采用……"
- 用动词开头代替"进行 X 操作"句式
- 用具体数字代替"显著提升"等模糊副词

### 2.2 以读者为中心

- 写"用户登录后看到 Dashboard 页面"而不是"本系统实现了登录模块"
- 写"运行 `make up` 后访问 `http://localhost:8080`"而不是"启动方法如以下命令所示"
- 默认读者熟悉 Docker、Python、Vue 基础，不需要解释什么是容器、什么是 ORM

### 2.3 任务可执行

- 每个章节都应回答"读者读完这一节能做什么"
- 命令、配置、路径必须可复制粘贴
- 所有示例必须经过实际验证

### 2.4 不重复造词

- 同一概念在全文使用同一中文译名
- 自造抽象词每段最多 1 个，必要时配英文原文
- 优先复用 `06-01-使用手册.md` 已定义的名词

## 三、禁止内容

### 3.1 绝对禁止

| 类别 | 禁止示例 | 替代方案 |
|---|---|---|
| 学术体例 | 摘要、Abstract、关键词、Keywords | 不使用；用"概览"代替"摘要" |
| 论文术语 | 论文、毕业论文、答辩、答辩材料、评阅、评阅人 | 删除或改为"系统"、"项目"、"上线" |
| 学术章节 | 第 X 章、3.2.1、参考文献、References | 不使用；用"功能模块"、"接口列表" |
| 研究语言 | 本研究、本文、本论文、旨在、综上、综上所述、据此 | 删除主语，直接陈述 |
| 致谢 | 致谢、Acknowledgment、致谢辞 | 删除 |
| 公式块 | LaTeX 公式、算法伪代码 | 改为代码块或表格 |
| 学术修饰 | 一定程度上、显著、大幅、有效、良好 | 删除或换为具体数字 |
| 主观判断 | 创新点、突破、独创、领先、特色 | 删除 |
| 引用说明 | 在正文中列出"参考文献""引用格式""参考文献标注指南"等说明性文字 | 不出现此类章节；技术细节直接写入正文 |
| 引用声明 | `> **本节件已按 [规范] 修订：YYYY-MM-DD**` | 删除，git blame 即可追溯 |
| 文档头元信息 | `> **版本** / **编制日期** / **覆盖时间** / **目标** / **适用** / **范围** / **作者** / **维护人** 等键 | 删除，git commit 元数据已包含 |
| 敏感词 | 导师、学院、专业、班级、学号 | 删除 |

### 3.2 高度警惕

| 类型 | 示例 | 处理建议 |
|---|---|---|
| "用于论文图表" | 表格中"用途"列写"用于论文图表" | 改为"用于 Dashboard 展示"或具体场景 |
| "不在论文范围内" | 出现在规划文档中 | 改为"当前版本不实现"或"v2.0 规划中" |
| 章节号引用 | "第 3 章 3.3.1" | 删除或改为文档内的章节号 |
| 过期路径 | `d:\works\WorkBuddy\Myhome\毕业论文设计与实现\...` | 改为 `d:\works\WorkBuddy\Myhome\ThesisDesignImplementation\...` |

## 四、必须使用的描述方式

### 4.1 描述功能时

- 写"做什么"和"怎么用"
- 列举接口时附上方法、路径、入参、返回、错误码
- 列举配置项时附上类型、默认值、是否必填

### 4.2 描述流程时

- 使用步骤编号 + 命令/操作的格式
- 关键决策点用"⚠️"标注
- 时序逻辑用流程图或时序图，不写"首先……然后……最后……"

### 4.3 描述问题时

- 描述现象（错误信息、日志、截图）
- 描述根因（具体到代码位置或配置项）
- 描述解决方案（具体到命令或代码变更）
- 不写"经过分析发现"、"深入研究发现"

### 4.4 描述数据时

- 给绝对值（"耗时 12ms"）而不是相对值（"性能提升 60%"）
- 给单位（"5 类 × 200 张 × 5 epoch"）
- 给测试环境（"CPU：i7-12700H，内存 32GB"）

### 4.5 描述变更时

- 写"修改了哪个文件、修改了什么"
- 写"为什么修改"
- 写"影响范围"
- 不写"重构了 X 模块使之更符合 Y 原则"

## 五、结构与版式规范

### 5.1 文档结构

```
# 文档标题（H1，唯一）

> 关键元信息（版本、日期、范围、维护人）

---

## 一级章节（H2，使用中文数字"一、二、三"或"概述/功能/接口/运维"）

### 二级章节（H3，使用"1.1、1.2"或"功能描述/接口列表"）

#### 三级章节（H4，按需使用）
```

### 5.2 元信息块（2026-08-10 修订：禁止）

**禁止在文档开头或正文出现"引用说明性文字"**：

- 禁止 `> **本节件已按 [00-00-文档风格规范](...) 修订：YYYY-MM-DD**` 这类声明
- 禁止 `> **版本** / **编制日期** / **覆盖时间** / **目标** / **适用** / **范围** / **作者** / **日期** / **基线 commit** / **维护人** / **冻结日期** / **Git Tag**` 等键的元信息块
- 禁止 `**编制日期**` / `**版本**` / `**关联文档**` 这种不带 `>` 前缀的元信息行
- 禁止 `- **键**: 值` 列表形式的元信息行
- 禁止 `第 X 章 X.X.X` 章节号引用
- 禁止 H1 内的 BOM 残留

历史版本信息通过 git 提交记录查询，**不在文档中重复声明**。需要追溯某段内容时，git blame 即可。

文档结构按以下范式：

```markdown
# 文档标题（H1，唯一）

## 一级章节（H2）

### 二级章节（H3）

#### 三级章节（H4）
```

### 5.3 表格与代码

- 表格用于对比、列表、参数说明
- 代码块必须标注语言（`bash`、`python`、`yaml`、`json`）
- 关键命令加粗以提示

### 5.4 强调与样式

| 用途 | 样式 | 示例 |
|---|---|---|
| 路径/命令/标识符 | 行内代码 | `docker compose up -d` |
| 必填项/危险操作 | 粗体 | **生产环境请先备份** |
| 章节小标题 | 三级粗体 | **关键决策** |
| 提示/警告 | 引用块 + ⚠️ | > ⚠️ 警告内容 |

### 5.5 禁用样式

- 禁用斜体（`*xxx*`）除变量占位外
- 禁用删除线（`~~xxx~~`）
- 禁用 emoji（`✅`、`❌`、`🚀` 等）除 ⚠️ 之外
- 禁用 H1 以外的中文标点（如"——"长破折号，可用半角"-"代替）

## 七、文件命名与目录组织

### 7.1 命名规则

- 使用双段编号 `NN-XX-名称.md`（如 `06-01-使用手册.md`）
- 中文名称用全角连接"-"，英文用半角
- 不带空格、不带特殊字符
- 同一主题最多 2 段编号

### 7.2 目录分层

```
docs/                          # 项目级文档
├── 00-00-README.md            # 总入口
├── 00-00-文档风格规范.md      # 本文件
├── 00-01-文档审核清单.md      # 配套审核清单
├── 01-xx 系统设计
├── 02-xx 实现记录
├── 03-xx 功能完善
├── 04-xx 测试与评估
├── 05-xx 代码冻结
├── 06-xx 使用与说明
├── 07-xx 部署与运维
├── 08-xx 发布说明
├── 09-xx 子项目（团队管理等）
├── task-summaries/            # 单任务完成报告
└── archive/                   # 已归档（不再修订）
    └── 00-ARCHIVED.md         # 归档说明
```

### 7.3 archive/ 处理规则

- 进入 `archive/` 的文件**不再修改内容**
- 在文件开头插入统一归档声明（脚本自动完成）
- 保持文件名不变以便历史链接不失效

## 八、文档审核机制

### 8.1 提交前自查清单

提交前对照 `00-01-文档审核清单.md` 逐项打勾。

### 8.2 自动检查脚本

提供 `scripts/check_docs_style.py` 脚本（计划中），执行以下检查：

- 检测"论文"、"摘要"、"致谢"等禁止词
- 检测过期路径（`毕业论文设计与实现`）
- 检测中文章节编号错误

### 8.3 评审流程

```
开发编写 → 自我审核（清单）→ 同伴评审 → 合并
```

- 新文档：必须经过 1 名同伴评审
- 修改文档：影响 ≥ 10 行需同伴评审；< 10 行可作者自查
- 核心文档（README、使用手册）：必须经过 2 名评审

### 8.4 季度审查

- 每季度由文档维护人（可轮值）抽查 20% 文档
- 抽查结果记入 `04-01-文档审查记录.md`
- 发现的违规在下一季度内修复

## 九、违规处理流程

| 级别 | 情况 | 处理 |
|---|---|---|
| **L1 严重** | 含完整学术章节（摘要/致谢/引用说明） | 阻断合并；强制重写 |
| **L2 中度** | 多处（≥ 5 处）论文术语 | 打回修改；同伴评审通过后可合并 |
| **L3 轻度** | 1-4 处论文术语 | 作者自查修改后合并；季度审查复核 |
| **L4 提示** | 个别过期路径 | 文档维护人集中处理 |
