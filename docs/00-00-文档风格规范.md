# 文档风格规范

> **版本**: v1.5
> **生效日期**: 2026-08-13
> **适用范围**: `docs/`、`backend/docs/`、`frontend/docs/`、`deploy/docs/` 下所有 Markdown 文档
> **维护人**: 项目全体开发与文档维护人员

本规范定义项目内部技术文档的写作要求。规范面向项目交付物本身，目的是让所有技术文档保持一致、可执行、易维护。

---

## 一、文档定位

本项目所有 `*.md` 文档均为**工程交付文档**，服务于：

- 工程师快速理解模块职责、接口契约、配置项、操作步骤
- 运维人员按文档完成部署、监控、故障恢复
- 新成员按文档完成环境搭建与首次使用
- 记录实现决策、变更历史、已知问题

---

## 二、风格总则

### 2.1 直接陈述事实

- 用"是什么"代替"为了实现……，本文采用……"
- 用动词开头代替"进行 X 操作"句式
- 用具体数字代替"显著提升"等模糊副词

### 2.2 以读者为中心

- 写"用户登录后看到 Dashboard 页面"而不是"本系统实现了登录模块"
- 写"运行 `make up` 后访问 `http://localhost:8080`"而不是"启动方法如以下命令所示"
- 默认读者熟悉 Docker、Python、Vue 基础，不需要解释什么是容器、什么是 ORM

### 2.3 任务可执行

- 每个章节都应回答"读者读完这一节能做什么"
- 命令、配置、路径必须可复制粘贴
- 所有示例必须经过实际验证

### 2.4 不重复造词

- 同一概念在全文使用同一中文译名
- 自造抽象词每段最多 1 个，必要时配英文原文
- 优先复用 `06-01-使用手册.md` 已定义的名词

## 三、禁止内容

### 3.1 绝对禁止

| 类别 | 禁止示例 | 替代方案 |
|---|---|---|
| 抽象修饰 | 显著、大幅、有效、良好 | 删除或换为具体数字 |
| 主观判断 | 自夸性形容词 | 删除 |
| 说明性区块 | 在正文中列出无关的"使用指南""标注规则" | 不出现此类章节；技术细节直接写入正文 |
| 引用声明 | `> **本节件已按 [规范] 修订：YYYY-MM-DD**` | 删除，git blame 即可追溯 |
| 文档头元信息 | `> **版本** / **编制日期** / **覆盖时间** / **目标** / **适用** / **范围** / **作者** / **维护人** 等键 | 删除，git commit 元数据已包含 |

### 3.2 高度警惕

| 类型 | 示例 | 处理建议 |
|---|---|---|
| 模糊场景描述 | 表格中"用途"列写"用于 X 文档" | 改为"用于 Dashboard 展示"或具体业务场景 |
| 范围表达不清 | 出现在规划文档中"不做此功能" | 改为"当前版本不实现"或"v2.0 规划中" |
| 过期路径 | `d:\works\WorkBuddy\Myhome\旧路径\...` | 改为 `d:\works\WorkBuddy\Myhome\ThesisDesignImplementation\...` |

## 四、必须使用的描述方式

### 4.1 描述功能时

- 写"做什么"和"怎么用"
- 列举接口时附上方法、路径、入参、返回、错误码
- 列举配置项时附上类型、默认值、是否必填

### 4.2 描述流程时

- 使用步骤编号 + 命令/操作的格式
- 关键决策点用"⚠️"标注
- 时序逻辑用流程图或时序图，不写"首先……然后……最后……"

### 4.3 描述问题时

- 描述现象（错误信息、日志、截图）
- 描述根因（具体到代码位置或配置项）
- 描述解决方案（具体到命令或代码变更）
- 不写"经过分析发现"、"深入研究发现"

### 4.4 描述数据时

- 给绝对值（"耗时 12ms"）而不是相对值（"性能提升 60%"）
- 给单位（"5 类 × 200 张 × 5 epoch"）
- 给测试环境（"CPU：i7-12700H，内存 32GB"）

### 4.5 描述变更时

- 写"修改了哪个文件、修改了什么"
- 写"为什么修改"
- 写"影响范围"
- 不写"重构了 X 模块使之更符合 Y 原则"

## 五、结构与版式规范

### 5.1 文档结构

```markdown
# 文档标题（H1，唯一）

## 一级章节（H2，使用中文数字"一、二、三"或"概述/功能/接口/运维"）

### 二级章节（H3，使用"1.1、1.2"或"功能描述/接口列表"）

#### 三级章节（H4，按需使用）
```

### 5.2 元信息块（禁止）

**禁止在文档开头或正文出现"元说明性文字"**：

- 禁止 `> **本节件已按 [00-00-文档风格规范](...) 修订：YYYY-MM-DD**` 这类声明
- 禁止 `> **版本** / **编制日期** / **覆盖时间** / **目标** / **适用** / **范围** / **作者** / **日期** / **基线 commit** / **维护人** / **冻结日期** / **Git Tag**` 等键的元信息块
- 禁止 `**编制日期**` / `**版本**` / `**关联文档**` 这种不带 `>` 前缀的元信息行
- 禁止 `- **键**: 值` 列表形式的元信息行
- 禁止 H1 内的 BOM 残留

历史版本信息通过 git 提交记录查询，**不在文档中重复声明**。需要追溯某段内容时，git blame 即可。

### 5.3 表格与代码

- 表格用于对比、列表、参数说明
- 代码块必须标注语言（`bash`、`python`、`yaml`、`json`）
- 关键命令加粗以提示

### 5.4 强调与样式

| 用途 | 样式 | 示例 |
|---|---|---|
| 路径/命令/标识符 | 行内代码 | `docker compose up -d` |
| 必填项/危险操作 | 粗体 | **生产环境请先备份** |
| 章节小标题 | 三级粗体 | **关键决策** |
| 提示/警告 | 引用块 + ⚠️ | > ⚠️ 警告内容 |

### 5.5 禁用样式

- 禁用斜体（`*xxx*`）除变量占位外
- 禁用删除线（`~~xxx~~`）
- 禁用 emoji（`✅`、`❌`、`🚀` 等）除 ⚠️ 之外
- 禁用 H1 以外的中文标点（如"——"长破折号，可用半角"-"代替）

## 六、术语替换对照

| 禁止使用 | 替换为 | 说明 |
|---|---|---|
| 一定程度上 | （删除） | 量化或删除 |
| 显著提升 | 给出具体数字 | 如"耗时从 4s 降至 1.2s" |
| 模糊场景描述 | 写明真实使用场景 | 改为"用于 Dashboard 展示"等 |
| 不在 X 范围 | 当前版本不实现 / v2.0 规划中 | 用项目版本语言 |

## 七、文件命名与目录组织

### 7.1 命名规则

- 使用双段编号 `NN-XX-名称.md`（如 `06-01-使用手册.md`）
- 中文名称用全角连接"-"，英文用半角
- 不带空格、不带特殊字符
- 同一主题最多 2 段编号

### 7.2 目录分层

```
docs/                          # 项目级文档
├── 00-00-README.md            # 总入口
├── 00-00-文档风格规范.md      # 本文件
├── 00-01-文档审核清单.md      # 配套审核清单
├── 01-xx 系统设计
├── 06-xx 使用与说明
├── 07-xx 部署与运维
├── 09-xx 子项目（团队管理等）
├── img/                       # 设计图、截图、流程图
└── archive/                   # 已归档（不再修订）
    └── 00-ARCHIVED.md         # 归档说明
```

### 7.3 archive/ 处理规则

- 进入 `archive/` 的文件**不再修改内容**
- 在文件开头插入统一归档声明（脚本自动完成）
- 保持文件名不变以便历史链接不失效

## 八、文档审核机制

### 8.1 提交前自查清单

提交前对照 `00-01-文档审核清单.md` 逐项打勾，核心项包括：

- [ ] 全文无自夸性主观判断
- [ ] 全文无"一定程度上 / 显著 / 大幅 / 有效 / 良好"等模糊副词
- [ ] 不在正文中出现无关的"使用指南"等说明性区块

### 8.2 自动检查脚本

提供 `scripts/check_docs_style.py` 脚本（计划中），执行以下检查：

- 检测模糊副词（显著、大幅、有效）
- 检测主观判断词
- 检测过期路径
- 检测中文章节编号错误

### 8.3 评审流程

```
开发编写 → 自我审核（清单）→ 同伴评审 → 合并
```

- 新文档：必须经过 1 名同伴评审
- 修改文档：影响 ≥ 10 行需同伴评审；< 10 行可作者自查
- 核心文档（README、使用手册）：必须经过 2 名评审

## 九、违规处理流程

| 级别 | 情况 | 处理 |
|---|---|---|
| **L1 严重** | 含完整违规章节、元说明区块 | 阻断合并；强制重写 |
| **L2 中度** | 多处（≥ 5 处）禁用术语 | 打回修改；同伴评审通过后可合并 |
| **L3 轻度** | 1-4 处禁用术语 | 作者自查修改后合并；季度审查复核 |
| **L4 提示** | 个别过期路径 | 文档维护人集中处理 |
