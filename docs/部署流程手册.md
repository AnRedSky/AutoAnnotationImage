## 0️⃣ 30 秒极简部署（推荐先看）

> **适用场景**: 不想读完整文档，只想尽快跑起来

### 0.1 前提条件

- 已安装 **Docker Desktop 4.x+**（含 `docker compose` v2.20+）
- 至少 **30 GB 可用磁盘空间**
- 主机端口 **3306 / 6379 / 8000 / 8080 / 9000 / 9001** 全部空闲

### 0.2 一行命令启动

**Windows（PowerShell）**:

```powershell
# 在项目根目录执行
.\scripts\start_docker.ps1
```

**Linux / macOS**:

```bash
# 在项目根目录执行
chmod +x scripts/start_docker.sh
./scripts/start_docker.sh
```

脚本会自动完成 6 步：

1. ✅ 检查 `.env`，不存在则从 `.env.example` 复制
2. ✅ 自动生成全部强随机密钥（覆盖 `CHANGEME` 占位符）
3. ✅ 校验 Docker / Compose 环境
4. ✅ 构建所有镜像（首次较慢，约 5-15 分钟）
5. ✅ 启动 7 个服务（mysql / redis / minio / api / worker-train / worker-annotate / frontend）
6. ✅ 等待服务 healthy 并运行端到端验证

### 0.3 启动后访问

| 服务 | URL | 默认凭据 |
| --- | --- | --- |
| 前端 | http://localhost:8080 | — |
| API 文档 | http://localhost:8000/docs | — |
| 健康检查 | http://localhost:8000/api/health | — |
| MinIO 控制台 | http://localhost:9001 | 见 `.env`（脚本自动生成） |
| MySQL | localhost:3306 | 见 `.env`（脚本自动生成） |

### 0.4 常用命令速查

```bash
# 状态
.\scripts\start_docker.ps1 -Status           # Windows
./scripts/start_docker.sh --status            # Linux/macOS

# 日志
.\scripts\start_docker.ps1 -Logs             # Windows
./scripts/start_docker.sh --logs              # Linux/macOS

# 停止
.\scripts\start_docker.ps1 -Stop             # Windows
./scripts/start_docker.sh --stop              # Linux/macOS

# 重新构建
.\scripts\start_docker.ps1 -Rebuild          # Windows
./scripts/start_docker.sh --rebuild          # Linux/macOS

# 重置数据（删除所有卷）
.\scripts\start_docker.ps1 -Reset            # Windows
./scripts/start_docker.sh --reset             # Linux/macOS
```

## 阶段 1️⃣ 准备（Preparation）

**目标**: 验证环境与配置正确性，杜绝"准备不足"导致的部署失败

### 1.1 任务清单

| # | 任务 | 验收标准 |
| --- | --- | --- |
| 1.1.1 | 检查 Docker / Compose 版本 | `docker --version` ≥ 20.10 / `docker compose version` ≥ v2.20 |
| 1.1.2 | 检查磁盘空间 | ≥ 30 GB 可用 |
| 1.1.3 | 检查端口占用 | 3306 / 6379 / 8000 / 8080 / 9000 / 9001 全部空闲 |
| 1.1.4 | 准备统一 .env 文件 | 见 §1.2 |
| 1.1.5 | 生成强密钥 | 见 §1.3 |
| 1.1.6 | 自定义业务配置 | 见 §1.4 |

### 1.2 准备统一 .env 文件（核心）

> ⚠️ **重要变更（v3.3.1 起）**: 系统现已统一从**项目根目录 `.env`** 读取所有环境变量，
> 不再使用 `backend/.env.docker` / `backend/.env.prod` 等多个分散文件。
>
> 这种设计的好处：
> 1. **一份配置 = 一处真相**（Single Source of Truth）
> 2. **Docker Compose 与后端代码看到完全相同的配置**
> 3. **避免"开发环境能跑、生产环境起不来"的偏差**

#### 1.2.1 首次部署

```bash
# 1) 进入项目根
cd <项目根目录>

# 2) 复制模板（如果 .env 不存在）
# Linux/macOS:
cp .env.example .env

# Windows (PowerShell):
Copy-Item .env.example .env

# 3) 后续由 start_docker 脚本自动生成密钥, 无需手动编辑
```

#### 1.2.2 文件位置

| 用途 | 路径 | 备注 |
| --- | --- | --- |
| **统一配置（唯一入口）** | `<项目根>/.env` | Docker Compose + 后端 pydantic-settings + 前端 Vite 同时读取 |
| 配置模板（可入库） | `<项目根>/.env.example` | 包含全部 `CHANGEME` 占位符 |
| 旧文件（已废弃） | `backend/.env.docker` | ⚠️ 不再使用，保留仅作历史归档 |
| 旧文件（已废弃） | `backend/.env.prod` | ⚠️ 不再使用 |

### 1.3 生成强密钥

#### 方式 A：自动（推荐）

由 `start_docker.ps1` / `start_docker.sh` / `gen_secrets.py` 自动完成：

```bash
# 一键启动脚本会自动调用:
python scripts/gen_secrets.py --write --env-file .env
```

#### 方式 B：手动

```bash
# SECRET_KEY (32+ 字符, JWT 签名)
python -c "import secrets; print(secrets.token_urlsafe(32))"

# MYSQL_ROOT_PASSWORD (16+ 字符)
python -c "import secrets; print(secrets.token_urlsafe(16))"

# MYSQL_PASSWORD (16+ 字符)
python -c "import secrets; print(secrets.token_urlsafe(16))"

# REDIS_PASSWORD (16+ 字符)
python -c "import secrets; print(secrets.token_urlsafe(16))"

# MINIO_ACCESS_KEY (8 字节, 满足 MinIO 用户名规范)
python -c "import secrets; print(secrets.token_urlsafe(8))"

# MINIO_SECRET_KEY (16+ 字符)
python -c "import secrets; print(secrets.token_urlsafe(16))"
```

将生成的字符串替换 `.env` 中对应的 `CHANGEME-...-CHANGEME` 占位符。

### 1.4 自定义业务配置

按需修改 `.env` 中以下项（其余保持默认即可）：

```ini
# ==== 必改：生产域名 ====
CORS_ORIGINS=https://your-domain.com,https://www.your-domain.com

# ==== 推荐：HuggingFace 镜像（国内网络必配）====
HF_ENDPOINT=https://hf-mirror.com

# ==== 按需：存储后端 ====
STORAGE_BACKEND=minio    # local | minio, 生产推荐 minio

# ==== 按需：推理设备 ====
INFERENCE_DEVICE=cpu    # cpu | cuda, 有 GPU 时改为 cuda
```

### 1.5 验收标准

```bash
# 1) .env 文件存在
ls -la .env                # Linux/macOS
Test-Path .env             # Windows PowerShell

# 2) 没有残留的 CHANGEME 占位符
grep "CHANGEME" .env       # Linux/macOS
Select-String -Path .env -Pattern "CHANGEME"   # Windows
# 期望: 无输出

# 3) 文件权限（仅 Linux 推荐）
chmod 600 .env
stat -c "%a" .env          # 期望: 600
```

## 阶段 2️⃣ 构建（Build）

**目标**: 编译多阶段镜像，最小化体积

### 2.1 任务清单

| # | 任务 | 验收标准 |
| --- | --- | --- |
| 2.1.1 | 拉取基础镜像 | `python:3.10-slim` / `mysql:8.0` / `redis:7-alpine` 等 |
| 2.1.2 | 构建多阶段镜像 | builder → base → api/worker |
| 2.1.3 | 镜像大小核查 | api/worker < 2 GB / frontend < 100 MB |
| 2.1.4 | 验证层缓存 | 依赖层独立、应用层独立 |

### 2.2 构建命令

#### 2.2.1 首次完整构建（推荐 `--no-cache` 确保干净）

```bash
# 拉取所有基础镜像
docker compose --env-file .env pull

# 完整构建 (耗时 5-15 分钟, 取决于网络)
docker compose --env-file .env build --no-cache --pull
```

#### 2.2.2 增量构建（日常开发）

```bash
# 仅修改了应用代码 (依赖未变)
docker compose --env-file .env build api

# 修改了 pyproject.toml / uv.lock
docker compose --env-file .env build --no-cache api worker-train worker-annotate
```

#### 2.2.3 一键启动脚本（最简单）

```bash
# Windows:
.\scripts\start_docker.ps1 -Rebuild

# Linux/macOS:
./scripts/start_docker.sh --rebuild
```

### 2.3 验证构建结果

```bash
# 查看镜像列表
docker images | grep annotation

# 期望:
# annotation/api:local       ~1.8 GB
# annotation/worker:local    ~1.8 GB
# annotation/frontend:local  ~55 MB

# 查看镜像层（验证多阶段）
docker history annotation/api:local | head -20

# 验证镜像可独立运行
docker run --rm annotation/api:local python -c "import fastapi; print(fastapi.__version__)"
# 期望: 0.110.0

# 验证构建工具已清除（最小镜像原则）
docker run --rm annotation/api:local which gcc
# 期望: (空) — gcc 不应在最终镜像中

docker run --rm annotation/api:local which curl
# 期望: /usr/bin/curl — curl 用于健康检查, 必须保留
```

### 2.4 验收标准

| 检查项 | 命令 | 期望 |
| --- | --- | --- |
| 镜像存在 | `docker images annotation/api:local` | 存在 |
| 镜像大小 | `docker images --format "{{.Size}}" annotation/api:local` | < 2 GB |
| 前端镜像 | `docker images annotation/frontend:local` | < 100 MB |
| 构建工具已移除 | `docker run --rm annotation/api:local which gcc` | 失败（无 gcc） |
| 健康检查依赖 | `docker run --rm annotation/api:local which curl` | `/usr/bin/curl` |
| Python 可执行 | `docker run --rm annotation/api:local python --version` | `Python 3.10.x` |
| Console script | `docker run --rm annotation/api:local which uvicorn` | `/app/.venv/bin/uvicorn` |

### 2.5 构建耗时说明

> **重要**: 首次构建会下载大量 Python 依赖（~1.8GB），请耐心等待。

| 阶段 | 耗时（首次） | 耗时（增量） |
| --- | --- | --- |
| 拉取基础镜像 (python:3.10-slim / ghcr.io/astral-sh/uv) | 1-3 min | 缓存命中，< 10s |
| apt-get 安装 (gcc, g++, curl) | 30-60s | 缓存命中，< 5s |
| **uv sync (拉取 PyPI 依赖)** | **5-15 min** | 缓存命中，< 30s |
| COPY 源码 + 健康检查 | 10-30s | 5-15s |
| **api 镜像总耗时** | **8-20 min** | **30-60s** |
| **worker 镜像（共用 builder）** | **复用 builder 缓存，1-3 min** | 10-30s |
| **frontend 镜像** | **3-5 min** | 30-60s |

**网络优化建议**:

```bash
# 1) 配置国内 PyPI 镜像 (推荐)
# 在项目根 .env 中追加:
UV_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple

# 2) 使用 BuildKit 并行构建
export DOCKER_BUILDKIT=1
export COMPOSE_DOCKER_CLI_BUILD=1
```

**断点续传**: 如果构建中断，再次运行 `.\scripts\start_docker.ps1` 会自动从缓存层继续，**无需重新下载已完成的层**。

## 阶段 4️⃣ 部署（Deploy）

**目标**: 编排全部服务上线

### 4.1 任务清单

| # | 任务 | 验收标准 |
| --- | --- | --- |
| 4.1.1 | 启动全部服务 | `docker compose up -d` |
| 4.1.2 | 验证启动顺序 | 应用等待基础设施 healthy 后启动 |
| 4.1.3 | 验证持久化卷 | volume 正确挂载 |
| 4.1.4 | 验证网络互通 | API → MySQL/Redis/MinIO 可达 |

### 4.2 部署命令

#### 4.2.1 一键部署（推荐）

```bash
# Windows:
.\scripts\start_docker.ps1

# Linux/macOS:
./scripts/start_docker.sh
```

#### 4.2.2 手动部署

```bash
# 1) 启动全部服务
docker compose --env-file .env up -d

# 2) 查看启动状态
docker compose --env-file .env ps
# 期望: 全部状态为 "running" 或 "healthy"

# 3) 查看启动日志
docker compose --env-file .env logs -f --tail=100
# Ctrl+C 退出 (服务在后台运行)

# 4) 单独查看某个服务
docker compose --env-file .env logs -f api
```

### 4.3 启动顺序验证

`depends_on` + `condition: service_healthy` 确保：

```
mysql (healthy) ─┐
redis (healthy) ─┼─→ api ─→ worker-train / worker-annotate
minio (healthy) ─┘             ↓
                              frontend
```

```bash
# 验证启动顺序
docker compose --env-file .env ps --format "table {{.Name}}\t{{.State}}\t{{.Status}}"
# 期望看到所有容器都 "Up" + "healthy" 状态
```

### 4.4 持久化卷验证

```bash
# 查看挂载的卷
docker compose --env-file .env ps --format "table {{.Name}}\t{{.Mounts}}"

# 或进入容器内验证
docker compose exec api ls -la /app/uploads /app/models /app/logs
# 期望: 三个目录存在且可写
```

### 4.5 网络验证

```bash
# 进入 API 容器测试网络
docker compose exec api bash
> nslookup mysql
> nslookup redis
> nslookup minio
# 期望: 解析到 172.x.x.x (bridge 网络)

> ping -c 2 mysql
> ping -c 2 redis
# 期望: 通

> curl -s http://minio:9000/minio/health/live
# 期望: 200 OK
```

### 4.6 验收标准

| 验收项 | 命令 / 标准 |
| --- | --- |
| 全部服务运行 | `docker compose ps` 全部 running |
| 健康检查通过 | 所有服务 healthcheck 状态为 healthy |

## 附录 A：统一 .env 配置体系

### A.1 配置体系总览（v3.3.1 新设计）

> **核心思想**: 一份 `.env` = 全栈所有组件的配置来源

```
┌─────────────────────────────────────────────────────────────────┐
│  <项目根>/.env          ← 唯一的配置入口 (Single Source of Truth) │
└────────────┬───────────────────┬───────────────────┬─────────────┘
             │                   │                   │
             │ env_file          │ pydantic-settings │ VITE_* ARG
             ▼                   ▼                   ▼
   ┌──────────────────┐ ┌──────────────────┐ ┌──────────────────┐
   │  Docker Compose  │ │  Backend (API +  │ │  Frontend Build  │
   │  (启动所有容器)  │ │  Worker)         │ │  (Vite 编译期)   │
   └──────────────────┘ └──────────────────┘ └──────────────────┘
```

### A.2 加载顺序与优先级

| 顺序 | 来源 | 适用 |
| --- | --- | --- |
| 1 | 操作系统环境变量 | CI/CD 注入的敏感值 |
| 2 | `<项目根>/.env` (项目根) | **统一配置入口（v3.3.1）** |
| 3 | `backend/.env` (兼容旧) | 仅当项目根 `.env` 不存在时回退 |
| 4 | 代码中的 `os.getenv` 默认值 | 仅开发模式 fallback |

### A.3 各服务的读取方式

| 服务 | 读取方式 | 代码位置 |
| --- | --- | --- |
| Docker Compose | `env_file: - .env` | `docker-compose.yml` |
| Backend (API + Worker) | pydantic-settings | `app/core/config.py` |
| Frontend (Build) | Vite `import.meta.env.VITE_*` | 构建时通过 `ARG VITE_API_BASE_URL` 注入 |

### A.4 关键变量对照表

| 变量 | Docker Compose 用途 | 后端用途 | 注意事项 |
| --- | --- | --- | --- |
| `MYSQL_HOST` | 健康检查、初始化 | SQLAlchemy 连接 | 容器内必须用 `mysql`（服务名） |
| `MYSQL_PASSWORD` | MySQL 初始化 | SQLAlchemy 鉴权 | 不能用默认 `root123/root` |
| `REDIS_PASSWORD` | Redis `--requirepass` | Celery broker | URL 中也要替换 |
| `CELERY_BROKER_URL` | — | Celery 连接 | 容器内用 `redis://:密码@redis:6379/1` |
| `MINIO_*` | MinIO root 凭据 | 对象存储客户端 | 容器内 endpoint = `minio:9000` |
| `CORS_ORIGINS` | — | FastAPI 中间件 | 改为实际前端域名 |
| `VITE_API_BASE_URL` | — | — | 空 = 同源（nginx 反代） |

### A.5 占位符与 fail-fast

`docker-compose.yml` 使用 `${VAR:?msg required}` 语法：

```yaml
MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD:?MYSQL_ROOT_PASSWORD required}
```

- 如果 `.env` 中该变量未设置或为 `CHANGEME-...-CHANGEME`，docker compose **直接报错并拒绝启动**
- 这避免了"忘记改默认密码就上线"的安全事故

### A.6 旧文件迁移指南

| 旧文件 | 状态 | 迁移动作 |
| --- | --- | --- |
| `backend/.env.docker` | ⚠️ 已废弃 | 内容已并入项目根 `.env.example` |
| `backend/.env.prod` | ⚠️ 已废弃 | 删除，统一用项目根 `.env` |
| `backend/.env.example` | ✅ 保留 | 后端开发者参考用（不影响部署） |

迁移步骤：

```bash
# 1) 备份旧文件
mv backend/.env.prod backend/.env.prod.bak 2>/dev/null || true

# 2) 使用统一 .env
cp .env.example .env
python scripts/gen_secrets.py --write --env-file .env

# 3) 根据需要把 .env.prod.bak 中的自定义值复制到 .env
```

## 附录 B：最小镜像原则

### B.1 多阶段构建原理

```
┌─────────────────────────────────────────────────────────────┐
│  builder stage (仅构建期)                                     │
│  python:3.10-slim + gcc g++ pkg-config                       │
│  uv sync (编译 C 扩展)                                       │
│  → /build/.venv                                              │
└──────────────────────┬───────────────────────────────────────┘
                       │  COPY --from=builder (仅 .venv)
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  base stage (最终 runtime 镜像)                               │
│  python:3.10-slim + curl ca-certificates (无 gcc/g++)         │
│  /app/.venv (从 builder 拷贝)                                  │
│  应用代码 / non-root 用户                                     │
│  → annotation/api:local / annotation/worker:local            │
└─────────────────────────────────────────────────────────────┘
```

### B.2 体积对比

| 组件 | 旧 (单 stage) | 新 (多 stage) | 节省 |
| --- | --- | --- | --- |
| python:3.10-slim | ~150 MB | ~150 MB | — |
| gcc + g++ + pkg-config | ~300 MB | — | -300 MB |
| 编译中间产物 (build/) | ~200 MB | — | -200 MB |
| 运行时依赖 | ~1.8 GB | ~1.8 GB | — |
| **合计** | **~2.5 GB** | **~1.8 GB** | **-28%** |

### B.3 关键最佳实践

1. **层缓存分离**：`pyproject.toml` + `uv.lock` 独立层 → 源码改动不破坏依赖缓存
2. **非 root 用户**：`USER app` 避免容器逃逸
3. **ENV 收敛**：`PATH=/app/.venv/bin:$PATH` 让 console scripts 可直接调用
4. **HEALTHCHECK 内置**：镜像自带健康检查，compose 可覆盖
5. **PYTHONDONTWRITEBYTECODE=1**：避免生成 .pyc 浪费时间
6. **PYTHONUNBUFFERED=1**：日志实时输出（docker logs 可看到）

### B.4 `.dockerignore` 作用

减少 build 上下文大小 → 加快 build 速度：

| 项 | 不排除时 | 排除后 |
| --- | --- | --- |
| .git/ | 几十 MB | 0 |
| node_modules/ | 几百 MB | 0 |
| .env / secrets | 几 KB (但泄露风险) | 0 |
| logs/ | 几十 MB | 0 |
| models/ | 几 GB | 0 |
| docs/ | 几 MB | 0 |

## 附录 C：常见故障排查

### C.1 部署脚本阶段

**Q: 启动脚本提示 "未找到 docker"？**
A: 安装 Docker Desktop 4.x+，并确保终端重启后 `docker --version` 正常。

**Q: 启动脚本提示 "未找到 docker compose"？**
A: Docker Desktop 4.x 已内置 `docker compose`（v2）。若使用旧版 Docker Toolbox，请先升级。

**Q: 密钥生成失败 / 替换占位符失败？**
A: 检查 `.env.example` 是否存在；检查 Python ≥ 3.6（`secrets` 模块需要）；可手动用 `python -c "import secrets; print(secrets.token_urlsafe(32))"` 生成。

### C.2 构建阶段

**Q: `uv sync` 失败 / 缓慢？**
A: 检查网络（HF 镜像）、`uv.lock` 是否与 `pyproject.toml` 同步。如网络不佳，在 `.env` 中配置国内 PyPI 镜像：

```bash
UV_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple
```

**Q: 首次构建需要多久？**
A: 见 §2.5「构建耗时说明」。完整流程 8-20 分钟（主要时间在 `uv sync` 下载 ~1.8GB 依赖）。

**Q: 构建过程被中断 / 失败了？**
A: 重新运行 `.\scripts\start_docker.ps1` 即可，BuildKit 会自动从缓存层继续。

**Q: 多阶段构建未生效，镜像仍 2.5GB？**
A: 确认 `docker buildx` 版本 ≥ 0.10，且 Dockerfile 第一行 `syntax=docker/dockerfile:1.7`。

**Q: 前端构建 `npm install` 太慢？**
A: 配置国内镜像：`npm config set registry https://registry.npmmirror.com`。

**Q: 构建输出无任何日志？**
A: 1) 确认 PowerShell 输出编码为 UTF-8：`[Console]::OutputEncoding = [System.Text.Encoding]::UTF8`
   2) 单独运行 `docker compose build api` 看是否有错误
   3) 检查 `docker system events` 是否还在产出事件

### C.3 启动阶段

**Q: API 一直重启？**
A: `docker compose logs api`，检查：

1. DB 连通（`MYSQL_HOST=mysql` 是否正确）
2. `.env` 中密码占位符是否已替换
3. 端口冲突

**Q: MySQL 启动慢？**
A: 首次启动需初始化（`start_period: 30s`），稍等再查。

**Q: 容器间无法通信？**
A:
1. 检查 `networks: annotation_net` 是否在所有服务中声明
2. 容器内必须用服务名（`mysql`/`redis`/`minio`）而非 `127.0.0.1`
3. 运行 `.\scripts\verify_inter_service.ps1` 详细诊断

**Q: 后端报错 "MYSQL_PASSWORD uses default/insecure value"？**
A: `APP_ENV=production` 启动时 `app.core.config._validate_production_secrets` 会 fail-fast 拒绝启动。请运行 `python scripts/gen_secrets.py --write --env-file .env` 重新生成密钥。

**Q: 跨容器 DNS 解析失败？**
A:
1. 确认所有服务都在 `annotation_net` 网络
2. 重启 compose: `docker compose down && docker compose up -d`
3. 检查 Docker Desktop 网络面板

**Q: MinIO / Redis 认证失败？**
A: 确认 `.env` 中 `REDIS_PASSWORD` / `MINIO_ACCESS_KEY` / `MINIO_SECRET_KEY` 三个值已替换（无 CHANGEME），且与 `docker-compose.yml` 中 `command:` 块完全一致。

### C.4 运行阶段

**Q: 训练任务一直 PENDING？**
A:

1. `docker compose logs worker-train`
2. 确认 `CELERY_BROKER_URL` 用容器服务名（`redis`）非 `127.0.0.1`
3. Redis 是否 healthy

**Q: SSE 断连？**
A: 检查反向代理（nginx）的 `proxy_buffering off` 与 `proxy_read_timeout` 设置。

**Q: 磁盘占满？**
A:

1. 检查日志卷：`docker system df`
2. 清理：`docker system prune -a`
3. 训练产物单独备份：定期清理 `model_data` 中过期权重

### C.5 安全相关

**Q: SECRET_KEY 泄露怎么办？**
A: 立即更换。所有已签发 Token 立即失效，用户需重新登录。

**Q: 怎么撤销已签发的 Token？**
A: 调用 `POST /api/auth/logout` 写黑名单，或修改 `SECRET_KEY` 强制全部失效。

**Q: 旧版本多 .env 文件还能用吗？**
A: `backend/.env.prod` / `backend/.env.docker` 仍能识别，但**强烈建议迁移到统一 `.env`**，避免配置漂移。详见 [附录 A.6](#a6-旧文件迁移指南)。

### C.6 升级与回滚

**Q: 如何升级到新版本？**
A:

```bash
git pull                                    # 拉取新代码
docker compose --env-file .env build         # 重新构建镜像
docker compose --env-file .env up -d         # 重启服务
```

**Q: 升级后发现问题，如何快速回滚？**
A:

```bash
# 1) 停止新版本
docker compose down

# 2) 切回旧代码
git checkout <旧版本-tag>

# 3) 重新构建并启动
docker compose --env-file .env build
docker compose --env-file .env up -d
```

**Q: 数据会丢失吗？**
A: 不会。MySQL / Redis / MinIO / 上传文件 / 训练产物都挂在独立 volume 上（`annotation_*_data`），仅 `docker compose down`（不带 `-v`）不会删除。
