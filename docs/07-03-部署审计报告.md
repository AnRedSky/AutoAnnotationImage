## 二、问题清单与修复建议

### 🔴 P0 关键问题（必须修复）

#### P0-1: `.env.docker` 包含明文默认密码
- **位置**: `backend/.env.docker` line 20, 33, 35, 46
- **影响**: 任何拿到镜像或代码的人可直接访问数据库
- **修复**: 改为占位符 + 强制外部注入

#### P0-2: `docker-compose.yml` 基础设施服务被注释
- **位置**: `docker-compose.yml` line 27-74
- **影响**: `depends_on` 也被注释，API 启动时无 MySQL/Redis/MinIO
- **修复**: 启用基础设施服务，配套完整依赖链

#### P0-3: 环境变量与实际部署端口不一致
- **位置**: `.env.docker` `MYSQL_PORT=3310`, `REDIS_PORT=9770`, `CELERY_BROKER_URL=redis://127.0.0.1:9770/1`
- **影响**: Worker 连接错误的端口
- **修复**: 统一为 compose 服务名引用

### 🟠 P1 重要问题（强烈建议修复）

#### P1-1: Dockerfile 单 stage 构建
- **位置**: `backend/Dockerfile`
- **影响**: `gcc g++` 等构建工具驻留最终镜像（~200MB 浪费）
- **修复**: 改为多阶段构建，builder 仅构建，runtime 仅含运行依赖

#### P1-2: 容器无资源限制
- **位置**: `docker-compose.yml`
- **影响**: 容器可耗尽宿主机资源
- **修复**: 添加 `mem_limit` / `cpus` / `pids_limit`

#### P1-3: 日志无轮转
- **位置**: `docker-compose.yml`
- **影响**: 容器日志无限增长占满磁盘
- **修复**: 配置 `logging.driver` + `max-size` / `max-file`

#### P1-4: `.dockerignore` 不完整
- **位置**: `backend/.dockerignore`
- **影响**: `.env` / 压缩包 / 训练产物可能进镜像
- **修复**: 补全忽略规则

### 🟡 P2 建议优化

#### P2-1: base 镜像用 `python:3.10-slim` (≈150MB) 而非 `alpine` (≈50MB)
- **决策**: 保留 slim。alpine 上 PyTorch / opencv / ultralytics 兼容性差，musl libc 与 glibc 行为差异导致隐藏 bug

#### P2-2: base stage 的 HEALTHCHECK 引用未定义的 `APP_PORT`
- **修复**: 改为硬编码或 base 显式设 ENV

## 三、最小镜像原则落地

### 3.1 多阶段构建设计

```
[builder stage]                     [runtime stage]
python:3.10-slim                    python:3.10-slim
  + gcc, g++, pkg-config, libpq      (无构建工具)
  + uv                              + 仅 runtime 依赖
  + uv sync (编译)                   + 应用代码
  + 编译所有 C 扩展                  + 非 root 用户
  ↓                                  ↓
  /app/.venv ─────────────────→  /app/.venv
  (拷贝而非继承)
```

### 3.2 体积估算

| 镜像 | 旧 | 新 | 节省 |
|---|---|---|---|
| `annotation/api:local` | ~2.5 GB | ~1.8 GB | ~28% |
| `annotation/worker:local` | ~2.5 GB | ~1.8 GB | ~28% |

主要削减来源：
- 移除 `gcc` (~150MB) / `g++` (~150MB) / `pkg-config` (~5MB)
- 移除 `ca-certificates` 之外的其他 apt 包
- 清理 apt 缓存（已做）

### 3.3 安全收敛

- ✅ 非 root 用户运行
- ✅ 无 `apt-get` 历史缓存（`rm -rf /var/lib/apt/lists/*`）
- ✅ 不暴露 `SECRET_KEY` / `MYSQL_PASSWORD` 默认值
- ✅ 健康检查 `HEALTHCHECK` 端到端可达

## 四、分阶段部署流程

### 阶段 1️⃣ 准备（Preparation）

**目标**: 验证环境与配置正确性
**任务**:
1. 检查 Docker / Docker Compose 版本
2. 准备 `.env.docker`（从模板）
3. 生成强密钥
4. 准备持久化目录权限
**验收标准**:
- `docker --version` ≥ 20.10
- `docker compose version` ≥ v2
- `.env.docker` 不含默认密码

### 阶段 2️⃣ 构建（Build）

**目标**: 编译多阶段镜像，最小化体积
**任务**:
1. `docker compose build --no-cache`（首次）
2. 镜像大小核查
3. 层缓存验证（依赖层与应用层分离）
**验收标准**:
- 镜像成功构建
- 体积 < 2 GB
- 镜像可独立运行 `docker run`

### 阶段 3️⃣ 测试（Test）

**目标**: 镜像在隔离环境验证
**任务**:
1. 启动基础设施
2. 运行健康检查
3. 运行 E2E 测试
**验收标准**:
- `/api/health` 返回 200
- pytest 套件全过
- 端到端业务流程通过

### 阶段 4️⃣ 部署（Deploy）

**目标**: 编排全部服务上线
**任务**:
1. `docker compose up -d`
2. 验证启动顺序（依赖健康）
3. 验证持久化卷挂载
**验收标准**:
- 所有服务 `running` 状态
- 健康检查连续 5 次通过
- 网络互通（API → MySQL/Redis/MinIO）

### 阶段 5️⃣ 验证（Verify）

**目标**: 端到端真实业务验证
**任务**:
1. 登录测试
2. 上传测试
3. 标注测试
4. 训练测试
5. 导出测试
**验收标准**:
- 业务流程完整跑通
- 性能指标达标（API 响应 < 500ms）
- 资源占用 < limit
